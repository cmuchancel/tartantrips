================================
PRIMARY OBJECTIVES
================================

Objective A. Centralize trip writes behind backend routes

The following writes currently still bypass the hardened backend:
- Web trip create/update in `app/plan/page.tsx`
- Web trip delete in `app/trips/page.tsx`
- Some web trip status updates in `app/trips/page.tsx`
- iOS trip save/delete in `ios/TartanTrips/Services/TartanTripsService.swift`

You must replace those direct writes with backend route calls.

Target state:
- Web clients call Next.js API routes for create/update/delete/status operations.
- iOS client calls the same backend API surface where appropriate.
- Business rules are enforced on the server, not trusted to the client.

Objective B. Move match transitions to a DB transaction or RPC

The following match actions are still orchestrated in JavaScript:
- request
- withdraw
- accept
- deny
- remove

Those operations can update multiple rows and currently depend on application-level rollback.

You must move them to a database-backed transactional boundary.

Preferred solution:
- Create a Postgres function or Supabase RPC that performs the full match transition atomically.
- Route handlers should validate/authenticate, then call the RPC.
- The RPC should either commit the full transition or fail with no partial write.

Fallback only if absolutely blocked:
- If a full RPC cannot be fully wired locally, still create:
  - the SQL migration or SQL file
  - the backend wrapper code
  - the route integration point
  - tests for the wrapper behavior
  - a clear note on what would be applied in Supabase

Objective C. Make match notification triggering durable

The current notification trigger path is operationally weak:
- Web triggers notifications from `app/plan/page.tsx` after saving a trip.
- iOS triggers notifications from `ios/TartanTrips/Services/TartanTripsService.swift`.
- Those client calls are fire-and-forget.
- A trip can save successfully while notification triggering fails, gets swallowed, or is skipped.
- There is no durable retry system today.

You must replace that model with a server-controlled durable workflow.

Preferred solution:
- Create a persistent notification job/outbox table, or equivalent durable record of pending notification work.
- Have trip create/update flows enqueue notification work on the server as part of the backend write path.
- Process pending notification work from a backend worker/cron/retryable route.
- Mark notification jobs with states such as `pending`, `processing`, `sent`, `failed`, and retry metadata if useful.

Fallback only if a full worker loop cannot be completed locally:
- Still add the durable persistence model for pending notification work.
- Add a backend processing path that can be called safely and idempotently.
- Ensure notification work is no longer dependent on a one-shot client trigger.
- Document exactly what scheduler/worker mechanism should be attached in deployment.

Objective D. Replace the slot-based match schema with a normalized pool + approval model

You must preserve the product concepts the user explicitly wants to keep:
- approval
- pool / rideshare group behavior
- multi-person pool expansion
- member removal
- pending decisions

Preferred normalized model:

1. `trips`
- remains the source of trip details
- no longer stores `match_email_*` or `match_status_*` as the primary relationship system

2. `ride_pools`
- one row per active rideshare group
- suggested fields:
  - `id`
  - `direction`
  - `flight_date`
  - `status` such as `active`, `completed`, `cancelled`
  - `created_by_trip_id`
  - `created_at`
  - `updated_at`

3. `ride_pool_members`
- one row per trip participating in a pool
- suggested fields:
  - `id`
  - `pool_id`
  - `trip_id`
  - `membership_status` such as `active`, `removed`
  - `joined_at`
  - `left_at`
- constraints:
  - foreign key to `ride_pools`
  - foreign key to `trips`
  - unique active membership per `(pool_id, trip_id)`
  - enforce maximum active members per pool through transaction/RPC logic

4. `pool_join_requests`
- one row per attempt by a trip to join another trip or existing pool
- this becomes the clean replacement for ad hoc `request_sent` / `request_received` slot coupling
- suggested fields:
  - `id`
  - `requester_trip_id`
  - `target_trip_id` nullable if request targets a pool directly
  - `target_pool_id` nullable if request targets a single trip
  - `status` such as `pending`, `withdrawn`, `accepted`, `denied`, `cancelled`, `completed`
  - `created_at`
  - `resolved_at`
- constraints:
  - foreign keys to `trips` and `ride_pools`
  - exactly one of `target_trip_id` or `target_pool_id` should be set

5. `pool_join_approvals`
- one row per required approver for a candidate joining a pool
- this is the clean replacement for `partner_approval_needed`
- suggested fields:
  - `id`
  - `join_request_id`
  - `approver_trip_id`
  - `decision` such as `pending`, `approved`, `denied`
  - `decided_at`
- constraints:
  - foreign key to `pool_join_requests`
  - foreign key to `trips`
  - unique `(join_request_id, approver_trip_id)`

6. `notification_jobs` or `notification_outbox`
- durable notification work queue

Clean state-model expectations:
- A two-person confirmed match becomes a `ride_pool` with two `ride_pool_members`.
- A request from one unmatched trip to another unmatched trip creates a `pool_join_request`.
- When accepted and no pool exists yet, create a new `ride_pool` and add both trips as members.
- When a trip requests to join an existing pool, create one `pool_join_request` and one `pool_join_approvals` row per active current member.
- When all approvals are `approved`, add the candidate to `ride_pool_members` and complete the request.
- If any approval is `denied`, mark the join request denied and do not add the candidate to the pool.
- Removing a member should update pool membership rows, not mutate six slot columns.

Strong preference:
- Migrate the application to this normalized schema as the new source of truth.
- If backward compatibility is temporarily required, provide a compatibility layer and migration plan, but do not treat the slot columns as the long-term design.

Fallback only if a full migration cannot be completed in one pass:
- add the new normalized schema and transaction/RPC layer
- add a compatibility adapter for current client views
- document a staged migration plan
- make the new schema the target architecture, not just an optional idea
